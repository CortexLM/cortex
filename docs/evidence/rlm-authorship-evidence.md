## Item 2 — TopicSetup journal: what lands, and with what provenance

**Claim.** An install lands migrations, routes, rules, the submission-format and scoring
digests, and the executor binding — and **the whole set is the RLM's** when its RLM authored
one, recorded per part.

### 2a. The journal schema

| Object | Migration | What it carries |
|---|---|---|
| `proof_topic_install` | `crates/db/migrations/0025_proof_topic_install.sql:48` | `topic_id`, `bundle_digest`, `environment`, `state`, `rules_version`, `rule_ids`, `migrations` (ordered), `binding` |
| `proof_topic_api` | `…0025…:88` | `topic_id`, `path` (topic-relative, no leading slash), `method`, `summary` |

`proof_topic_api` is the **dynamic route registry** — the challenge mounts it
(`challenge_router(state, topic_routes)`), so a topic's routes are served from the DB rather
than a compiled table.

`binding` now carries an **`authorship`** entry beside the executor it resolved
(`crates/proof-topic-install/src/install.rs:698` — the `authorship` object is built in `journal`):

```json
{
  "handler": "harbor", "runner_id": "…", "vms_per_submission": 1,
  "submission_format_digest": "sha256:…",
  "authorship": {
    "source": "rlm",
    "digest": "<whole-set digest>",
    "parts": {
      "rules":             {"source": "rlm", "version": 7, "digest": "sha256:…"},
      "migrations":        {"source": "rlm", "digest": "sha256:…", "names": ["0001_scratch"]},
      "apis":              {"source": "rlm", "digest": "sha256:…", "routes": ["GET /status"]},
      "submission_format": {"source": "rlm", "digest": "sha256:…"},
      "pin_policy":        {"source": "rlm", "digest": "sha256:…"}
    }
  }
}
```

An install from the **bundle** writes the same shape with `source: "topic_document"` and no
digests (`operator_authorship`). That is the distinction the publish gate reads, and it is
what makes "the RLM authored this topic" a per-part fact rather than a label on the row.

### 2c. Provenance: the RLM's set supersedes the bundle's section

`crates/proof-topic-install/src/install.rs:269`:

> **Whose set is this?** When the topic's own RLM authored one, that is the topic's behavior
> and the bundle's section is not applied: the RLM's answer supersedes the operator's
> declaration of intent, and the journal records `rlm` as the author of every part. The
> bundle's section is read only when no RLM set exists, and then with its own honest
> `topic_document` provenance — which the publish gate refuses to open a topic on.

`source = rlm` for the **rules** is reached only by the RLM running its own `propose_rules`
inside the topic VM. Enforced in three places:

| Gate | Path | Refuses |
|---|---|---|

| boot admission | `bins/proof-challenge/src/main.rs:854 load_topics` | an `open` doc whose install is not `applied` **or** whose rules are not RLM-authored (skipped, logged) |
| seal-time | `crates/proof-topic-setup/src/lib.rs:415` + `:439` | a measurement taken under a superseded / no-longer-in-force rule version |

### 2f. The boundary, as it now stands

The checklist asked to prove `migrations` / `apis` / `submission_format` / `pin_policy` are
**RLM-authored**. They are, and the wire carries them:

| Part | Who authors it | Where it lands | Enforced how |
|---|---|---|---|
| **rules** | **the RLM** (`propose_rules` in its topic VM) | `proof_rule_version.source='rlm'` | read-back (`proof-topic-setup/src/lib.rs:451`), boot admission (`bins/proof-challenge/src/main.rs:854`), seal-time version checks (`:415`, `:439`) |
| **migrations** | **the RLM** (`authoring.json`) | applied by the install, inside the topic's namespace | the deny-list runs **in the guest** (`proof-vm-guest/src/runner.rs:1085` — the guest's own deny-list run is `proof-topic-authoring/src/lib.rs:718`) and again at install (`proof-topic-install/src/install.rs`), plus the cross-topic claim check before the journal opens |
| **apis** | **the RLM** (`authoring.json`) | `proof_topic_api` rows | shape checks in the guest and at install; reserved-prefix check; the mux refuses an admin-namespace row on read |
| **submission_format** | **the RLM** (`authoring.json`) | digest in `binding.submission_format_digest` + `binding.authorship` | shape + canonical digest |
| **pin_policy** | **the RLM** (`authoring.json`) | digest in `binding.authorship` | shape, then **tighten-only**: a policy may raise a floor / lower a ceiling and never the reverse; three knobs are equalities (`eval_image_digest`, `gpu_class`, `holdout_size`) because every topic is measured against the same image and machine class. Held against the document in the guest (it has no pin) and against the pin on the control plane |
| `scoring` | **the RLM** (`authoring.json`) | digest in `binding.scoring_digest` | shape + canonical digest |
| `handler` | the **operator** | `binding.handler` | allow-list — a run backend is an operator capability (what was baked into the guest image), not something a topic chooses |

**How the set travels.** `VmJobOutput::Authored(Box<TopicAuthoring>)` is what a
`ProposeRules` job answers (`crates/proof-rlm/src/vm.rs:327`), and `VmJob::ProposeRules`
carries the set an RLM is re-authoring (`:212`). The document is one object with five parts
and `deny_unknown_fields`, so a part this build does not read is a refusal naming it rather
than a silent drop.

**A fragment is not authorship.** `VmJobOutput::Rules(Vec<ChecklistRule>)` survives for an
adaptor baked before the set existed. The host records the rules with honest `rlm`
provenance and **refuses to treat the topic as set up**
(`SetupError::IncompleteAuthoring`, naming the parts), because the parts it would fill in are
the operator's. The guest says the same thing in its own words
(`proof-vm-guest/src/runner.rs` `RULES_ONLY_IS_NOT_AUTHORSHIP`), and a test pins it
(`agent_tests.rs the_rlm_authors_its_whole_set_and_a_fragment_is_named_as_one`).

**Where the guest checks what it cannot check alone.** The guest holds an answer to the
deny-list and to the **document's own knobs** before it answers (`set.validate`,
`pin_policy.tightens_document`); the control plane holds it to the **pin**, which the guest
cannot see (`set.validate_against_pin`). Two processes, one description — both link
`proof-topic-authoring`, which is why they cannot disagree.

### 2g. The Owner LIVE run — moving the host onto the RLM's set

This is the step that turns §2d's "predates the change" into a live `authorship: rlm` row.
It is the operator's, not an agent's: it provisions a VM and runs a paid baseline.

**The set the RLM must author.** The adaptor's `propose_rules` entrypoint writes
`$PROOF_OUTPUT_DIR/authoring.json`:

```json
{
  "schema_version": 1,
  "topic_id": "<the topic>",
  "rules": [{"id": "no_short_circuit", "text": "the harness must run the task"}],
  "migrations": [{"name": "0001_scratch", "sql": "CREATE TABLE <topic>_scratch (id TEXT)"}],
  "apis": [{"path": "status", "method": "GET", "summary": "topic status"}],
  "submission_format": {"kind": "tar", "max_bytes": 5242880},
  "pin_policy": {}
}
```

Every part is required. `pin_policy` may be `{}` — that is the RLM saying "this topic
tightens nothing", which is a legitimate answer; **omitting** the key is not (the document
does not parse). A migration must sit inside the topic's own namespace (the same deny-list
an operator's bundle faces), and a route must be relative to the topic's prefix and outside
`v1/admin`.

**The commands** (staging first, metal only with the Owner's assertion):

```bash
# 1. The RLM authors and the install applies ITS set, then publishes.
#    Needs the topic-VM orchestrator + the RLM image digest + a live judge offer.
PROOF_VM_ORCHESTRATOR_URL=https://<kvm-host>:8200 \
PROOF_VM_ORCHESTRATOR_TOKEN_FILE=/run/base/proof/vm_orchestrator_token \
PROOF_RLM_VM_IMAGE_DIGEST=sha256:<pinned> \
PROOF_INFERENCE_OFFER_FILE=/run/base/proof/inference_offer.json \
BASE_DATABASE_URL=postgres://<master> \
  proof-admin topic install \
    --bundle <bundle>.json --env staging --drive-rlm --owner-approved \
    --admin-url https://<master> --admin-token-file /run/base/proof/admin_tokens

# 2. Read the measurement and the commitment the open document must seal.
proof-admin topic baseline <topic-id>

# 3. Put that commitment into the document, set `status: open`, sign it
#    (the `proof` key stays with the Owner), then seal and publish.
proof-admin topic seal <topic-id> --document <open>.json --publish \
  --admin-url https://<master> --admin-token-file /run/base/proof/admin_tokens

# 4. Prove it: the journal's newest row names the RLM as the author of every part.
proof-admin topic install-log --topic <topic-id> --json \
  | jq '.binding.authorship'
```

**What proves it worked — the journal entry, not the exit code:**

```
binding.authorship.source                == "rlm"
binding.authorship.parts.rules.source    == "rlm"
binding.authorship.parts.migrations.source == "rlm"
binding.authorship.parts.apis.source     == "rlm"
binding.authorship.parts.submission_format.source == "rlm"
binding.authorship.parts.pin_policy.source == "rlm"
```

and each part carries its own `digest` (and, for migrations and routes, the names that
landed). The install prints the set's digest in its report
(`DriveOutcome::summary`), so the operator sees it before the seal.

**Never the FIXED YAML.** The B1 run that took Gates 1–6 to GO was driven by a
human-authored YAML document (item 3e). That document has no path to being the SoT under
this change: a topic's behavior comes from `authoring.json` inside the VM, and a bundle
section is applied only when the RLM authored nothing — with `topic_document` provenance,
which the publish gate refuses to open a topic on. Re-running the Owner ceremony with the
FIXED YAML **cannot** produce an `authorship: rlm` row; it produces the old shape and the
gate says so.

## Item 3 — Source of truth is not an operator clone of legacy `tbench`

### 3e. The live SoT gap — B1 FIXED used a human YAML, and what changed

Dev's dig found the thing that matters: **the B1 FIXED run that took Gates 1–6 to GO was
driven by a human-authored YAML topic document.** That is not the final authorship SoT.

What pack v2 said about it, and what is true now:

| Question | pack v2 (before this tip) | now |
|---|---|---|
| Was the **rule vector** the RLM's? | **Yes** — v5–v7 all `source=rlm` **[staging]** | **Yes** — unchanged |
| Was the **document** (statement, metric, constraints, floors, pack pin) the RLM's? | **No** — an operator wrote it | **The document is still the operator's** — a signed `TopicDocument` is what miners are scored against, and it stays the operator's to publish. What the RLM owns is the **behavior**: rules, migrations, APIs, submission format, pin policy |
| Could the **behavior** be the RLM's? | **No** — no job or wire message carried it (§2f of pack v2) | **Yes** — `authoring.json`, one document, five parts (§2f) |
| Does a human YAML have a path to being served? | **No** — the host serves `proof_topic_version` and admits only `applied` + RLM-authored | **No, and now for a second reason**: even an install driven from a bundle records `topic_document` provenance, which the publish gate refuses to open |
| So is the SoT "operator clone of legacy tbench"? | **No** — but it is *operator-authored* | **No** — the behavior is the RLM's, and the journal proves it per part |

**The honest distinction that remains.** A topic's **document** (its statement, metric,
floors, and the pack pin) is operator-published, and that is by design: miners need a signed
document to be scored against, and only the operator holds the `proof` key. What this change
moves to the RLM is the topic's **behavior** — the five parts the checklist names. The
architecture's deeper intent ("the topic authors itself") is therefore met for behavior and
not for the document; saying otherwise would be rounding up, and the pack does not.

**Diff vs a human-minted `tb4` YAML:** there is no such YAML **in this repo** to diff
against. The live B1 YAML is operator-held on staging, outside this repo. The check that
matters is the one above — the host only serves what `proof_topic_version` holds under an
`applied` install, and the behavior it serves is the RLM's or the gate refuses to open.

## Security fixes found during this review (not authorship items)

Three P1 findings, each reproduced independently before fixing. The first is from the earlier
tip; the second and third are Greptile's findings on that fix, and both are in the same
registry-visible check.

### 1. Prefix-overlapping namespaces

The migration deny-list namespaces objects by the topic's mapped prefix (`-` → `_`), and
**prefixes are not prefix-free**. `aa` and `aa-b` are both legal ids; `aa_b_scratch` reads as
`aa` + `b_scratch` **and** as `aa-b` + `scratch`, so a migration approved for `aa` could
create, read, or drop a table belonging to `aa-b` in the shared database.

**The per-topic guard cannot fix this** — it sees one topic, and refusing every name with an
underscore after the prefix would refuse ordinary names like `tb4_scratch_idx` (including the
live shape's own index naming). The question is about the **registry**, so it is answered
where the registry is visible: `proof_topic_sql_guard::claim_collisions` reports any name
another registered topic also claims.

### 2. Function bodies bypassed the check (Greptile P1)

The check scanned `statement.blanked` — the statement with string literals **and
dollar-quoted function bodies** blanked — so object names *inside* a body were never compared
to the registry. Greptile's reproduction: topic `aa` installs
`CREATE FUNCTION aa_delete_sibling() … $$ DELETE FROM aa_b_scratch $$ LANGUAGE sql` while
sibling `aa-b` is registered, the install completes, and calling the function deletes the
sibling's rows.

**The body is what runs, so the body is what the check reads.** `collision_in` now scans both
`statement.blanked` and `statement.bodies`.

### 3. Unpublished installs were invisible, and the check was not atomic (Greptile P1)

The check enumerated `proof_topic_version` only, so a topic that had **installed but not yet
published** was invisible to it: `aa` and `aa-b` could both install and both create
`aa_b_scratch`. A topic claims a namespace by installing into it, so the claim has to be read
from the **journal** too. And under READ COMMITTED two concurrent installs each see no row
from the other and both commit — the same defect with a race on top.

**Both are closed in one place.** `Installer::claim_namespace` is a single transaction that

1. takes `pg_advisory_xact_lock` (the pattern this repo already uses for the alias slug race,
   `proof-rlm-store`), so two installs cannot interleave;
2. reads the union of `proof_topic_version` and `proof_topic_install` — every topic with a
   published document **or** an install row, which is what "registered" means; and
3. writes the `pending` row that records the claim **inside the same transaction**, so the
   next install to take the lock sees it.

A refusal rolls back, so it writes nothing at all — no row, no rule, no table.

**Tests, each verified non-vacuous** (neutering the fix makes the test fail):

| Test | What it pins |
|---|---|
| `a_function_body_that_reaches_a_sibling_is_refused` | the body scan; asserts the refusal names `aa_b_scratch` and that neither a journal row nor the function exists |
| `two_unpublished_installs_cannot_claim_the_same_object` | the journal half of the registry read; `aa-b` is never published, and the refusal still names it |
| `two_concurrent_installs_cannot_both_claim_a_namespace` | the atomicity; two racing installs, exactly one refused |
| `a_migration_that_reaches_a_sibling_topics_namespace_is_refused` | the original collision, end to end |
| guard-level `a_bare_name_two_topics_claim_is_reported_as_a_collision`, `a_name_no_registered_sibling_claims_is_not_a_collision` | `claim_collisions` itself |
